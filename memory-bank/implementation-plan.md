# DanceCARD V1 实施计划

## 1. 使用说明

本计划面向负责实施舞卡 V1 的 AI 开发者。必须按顺序执行步骤；每次只完成一个步骤，在验证全部通过后再进入下一步。任何测试失败时，先修复当前步骤，不得通过跳过、删除或弱化测试继续推进。

需求基准为 `memory-bank/Design-Document.md`，技术基准为 `memory-bank/tech-stack.md`。

严格遵守以下边界：

- V1 只做信息展示和联系方式连接，不实现支付、交易担保、聊天、购买记录、收藏、举报、定位或已售出状态。
- 用户端采用 Taro 4、React、TypeScript、Vite、NutUI Taro 和 SCSS。
- 后端采用 CloudBase Auth、CloudBase PostgreSQL 及 Node.js/TypeScript 云函数。
- 管理后台采用 React、Vite、TypeScript 和 Ant Design。
- V1 正式发布 H5；微信端只要求构建成功并通过微信开发者工具冒烟测试，不实现微信登录、不提交审核、不发布且不要求真机验收。
- 任何重大功能或里程碑完成后，必须更新 `memory-bank/architecture.md` 和 `memory-bank/progress.md`。

## 2. 里程碑一：建立实施基线

### 步骤 1：初始化 Memory Bank 记录

**指令：** 完整阅读 `memory-bank/Design-Document.md`、`memory-bank/tech-stack.md` 和本实施计划；在 `memory-bank/architecture.md` 记录当前技术栈、计划目录、系统边界和“尚未开始实施”的状态；在 `memory-bank/progress.md` 建立里程碑进度记录。

**验证：** 确认五个 Markdown 文件和 `memory-bank/assets/ui-reference.png` 都存在且可完整读取；确认 architecture 和 progress 的初始内容与仓库实际状态一致，没有虚构已完成功能。

### 步骤 2：建立需求追踪表

**指令：** 将 Design Document 中 12 条 V1 验收标准整理为可勾选的需求追踪表，并为每条标准标明预期的单元测试、组件测试或端到端测试类型。

**验证：** 逐条核对原文，确认 12 条标准无遗漏、无新增范围，每条至少关联一种验证方式。

### 步骤 3：确认 Git 与仓库边界

**指令：** 检查现有 Git 仓库、`main` 分支和首次文档提交；配置忽略依赖、构建产物、测试报告、CloudBase 本地状态和所有本地环境变量文件；保留环境变量示例文件的跟踪能力。

**验证：** 确认 Git 历史包含文档基线提交；创建临时的依赖目录、构建目录和本地环境文件，确认 Git 不跟踪它们；确认设计文档、迁移文件和环境变量示例仍可被跟踪；删除临时验证内容。

### 步骤 4：记录基线里程碑

**指令：** 更新 `memory-bank/architecture.md` 和 `memory-bank/progress.md`，记录文档来源、需求追踪方式、仓库当前状态和下一里程碑入口条件。

**验证：** 重新阅读 `memory-bank/architecture.md` 和 `memory-bank/progress.md`，确认内容与实际文件结构及进度一致，并明确写出“编码前必须阅读两份 Memory Bank 文档”。

## 3. 里程碑二：搭建工程骨架

### 步骤 5：创建 pnpm 工作区

**指令：** 建立根工作区以及 `apps`、`packages`、`cloudfunctions`、`database` 和 `e2e` 目录；配置所有后续项目从仓库根目录统一安装和运行。

**验证：** 执行依赖安装，确认工作区识别成功且锁文件唯一；检查不存在嵌套锁文件或重复依赖目录。

### 步骤 6：初始化 Taro 用户端

**指令：** 在 `apps/user-app` 使用 Taro 4 官方 React、TypeScript、Vite 模板初始化应用，锁定经过验证的具体版本。

**验证：** 分别完成 H5 开发构建、H5 生产构建和微信小程序生产构建；确认三者均无编译错误，且默认页面能在 H5 中打开。

### 步骤 7：接入移动端基础依赖

**指令：** 在用户端接入 NutUI Taro、SCSS 和 Zod，只完成依赖与构建配置，不实现业务页面。

**验证：** 在一个临时验证页分别渲染基础按钮、输入框和弹窗并加载 SCSS；确认 H5 和微信小程序构建均通过；验证结束后移除临时页面内容。

### 步骤 8：初始化管理后台

**指令：** 在 `apps/admin-web` 初始化 React、Vite、TypeScript 和 Ant Design 项目，只保留最小应用入口。

**验证：** 完成开发启动和生产构建；在桌面浏览器打开应用，确认无控制台错误和横向布局异常。

### 步骤 9：创建共享包

**指令：** 创建 `domain`、`validation`、`api-client` 和 `config` 四个共享包，配置明确的公开入口和单向依赖关系，避免应用之间相互引用源码。

**验证：** 让两个应用分别引用一个临时共享类型，运行全仓类型检查并确认解析成功；移除临时类型后再次确认类型检查通过。

### 步骤 10：建立代码质量工具

**指令：** 配置全仓 ESLint、Prettier 和 TypeScript 严格检查，并提供根级格式化、静态检查和类型检查入口。

**验证：** 用临时的不合规格式、未使用变量和类型错误分别触发三类检查，确认检查会失败；修复临时问题后确认全部检查通过。

### 步骤 11：建立测试基础设施

**指令：** 配置 Vitest、Testing Library 和 Playwright；为用户端、共享包和管理后台分别建立最小测试入口。

**验证：** 运行全仓单元测试和一个 H5 冒烟端到端测试，确认报告成功生成；故意制造一次失败断言，确认流水线会失败，再恢复测试。

### 步骤 12：建立环境配置规范

**指令：** 创建环境变量示例和环境说明，区分本地、测试与生产环境；禁止在客户端配置中出现服务端密钥。

**验证：** 搜索全部受版本控制文件，确认不存在真实密钥；在缺少必填配置时启动应用，确认能得到清晰错误提示，而不是静默失败。

### 步骤 13：记录工程骨架里程碑

**指令：** 更新 `memory-bank/architecture.md` 和 `memory-bank/progress.md`，记录真实目录、各应用职责、共享包依赖、构建目标、测试入口和当前完成进度。

**验证：** 将 architecture 中的目录和命令逐项与仓库核对；重新运行 H5、微信小程序和管理后台生产构建，确认里程碑可复现。

## 4. 里程碑三：建立领域规则与数据库

### 步骤 14：定义共享领域模型

**指令：** 在 domain 包定义用户、身份、城市、行政区域、舞室、次卡、可见性、隐藏原因和管理员操作的业务类型；保持登录身份与业务用户分离。

**验证：** 添加类型层测试，覆盖有效对象及禁止的状态组合；运行两个应用和云函数的类型检查，确认共享模型可被一致使用。

### 步骤 15：实现共享校验规则

**指令：** 在 validation 包建立次卡发布和编辑校验，覆盖 1–999 课时、最多两位小数的正价格、`Asia/Shanghai` 未过期日期、1–30 字昵称、1–50 字微信号、200 字使用限制、500 字备注、舞种范围、“其他”自定义名称及“全部舞种”和指定舞种互斥。

**验证：** 为每项规则至少测试一个有效值、边界值和无效值；确认错误信息能够明确定位字段。

### 步骤 16：创建 CloudBase 开发环境

**指令：** 创建独立的 CloudBase 开发环境并启用 PostgreSQL、Auth 和云函数；环境标识只写入本地配置和部署说明。

**验证：** 从本地执行一次只读连通性检查；确认能访问开发环境但无法访问未配置的生产环境；确认密钥未进入 Git 状态。

### 步骤 17：创建用户与身份表

**指令：** 编写第一组可回滚迁移，创建业务用户和多登录身份映射，并加入角色、账号状态、时间字段及必要唯一约束。

**验证：** 在空数据库执行迁移、回滚并再次执行；测试重复身份被拒绝、一个业务用户可关联多种不同身份、默认角色为普通用户。

### 步骤 18：创建城市与行政区域表

**指令：** 创建城市和行政区域表，加入启停状态、排序字段、外键和同一城市内区域名称唯一约束。

**验证：** 测试有效区域可关联城市、无效城市外键被拒绝、同城重名区域被拒绝、不同城市同名区域被允许。

### 步骤 19：创建舞室表

**指令：** 创建舞室表，关联行政区域并保存原始名称、标准化名称、可选地址、状态、创建管理员和时间字段；在同一行政区域内阻止标准化名称精确重复，不实现用户前台创建舞室。

**验证：** 测试舞室必须属于有效区域；确认停用状态可保存；确认同区域标准化名称精确重复被拒绝、相似名称仍可由管理员决定；确认删除被引用的区域时数据库不会产生孤立舞室。

### 步骤 20：创建次卡表

**指令：** 创建次卡表，完整覆盖 Design Document 字段、其他舞种自定义名称、发布时昵称和微信号快照、手动隐藏、管理员隐藏、过期原因和软删除时间；人民币金额使用精确十进制或分单位保存；不要添加已售出状态。

**验证：** 测试必填字段、正数约束、有效舞种组合和外键；确认数据库结构中不存在支付、订单、购买记录或已售出字段。

### 步骤 21：创建管理员操作日志

**指令：** 创建不可由普通用户写入的管理员操作日志，记录操作者、目标类型、目标标识、动作、原因和时间。

**验证：** 测试管理员操作可以留痕、普通用户直接写入被拒绝、删除目标后日志仍可保留审计信息。

### 步骤 22：添加索引与公开排序能力

**指令：** 为城市与区域排序、舞室筛选、公开次卡筛选、单节价格升序、发布时间倒序和每页 20 条的稳定分页添加必要索引。

**验证：** 使用包含多城市、多舞室和多价格的测试数据检查查询计划；确认同一舞室按价格升序、同价按发布时间倒序返回。

### 步骤 23：建立初始种子数据

**指令：** 创建可重复执行的种子数据：按 Design Document 录入北京、上海全部行政区和已核实的首批舞室；开发环境另加入普通用户、管理员以及公开、隐藏、过期次卡样例。正式录入舞室前再次核验营业状态，无法确认的门店以 inactive 状态保存。

**验证：** 连续执行两次种子流程，确认不会产生重复记录；逐项对照 Design Document 的两市区划、舞室名称、行政区和地址；检查每种次卡状态均有可用于后续测试的样例。

### 步骤 24：配置公共地理数据权限

**指令：** 为城市、行政区域和舞室配置 RLS，使游客只能读取启用记录，普通用户不能新增、修改或删除这些记录。

**验证：** 分别以游客、普通用户和管理员身份执行读写测试；确认停用记录不对游客显示，越权写入全部被拒绝。

### 步骤 25：配置公共次卡权限

**指令：** 建立公开次卡读取规则或公开视图，只返回未隐藏、未过期、未软删除、发布用户启用且所属城市、区域和舞室均启用的数据，并排除微信号；按每页 20 条稳定分页。

**验证：** 以游客查询所有样例，逐一停用用户、城市、区域和舞室并确认下属次卡停止公开但数据未删除；检查分页无重复或遗漏；确认任何列表和普通详情都没有微信号。

### 步骤 26：配置卖家所有权权限

**指令：** 配置次卡创建和修改的 RLS，使登录用户只能创建归属于自己、编辑自己的记录，且不能解除管理员隐藏。

**验证：** 用两个普通账号执行交叉操作；确认本人操作成功、修改他人记录失败、伪造 user_id 失败、恢复管理员隐藏失败。

### 步骤 27：配置管理员权限

**指令：** 配置管理员对城市、区域、舞室、次卡审核和用户状态管理的权限，并确保每个管理动作需要审计记录。

**验证：** 分别以普通用户和管理员执行同一组管理操作；确认只有管理员成功，且成功操作均产生内容正确的日志。

### 步骤 28：实现联系方式受保护接口

**指令：** 建立仅按单张公开次卡获取卖家微信号的云函数；函数必须再次检查用户、城市、区域、舞室、次卡状态和截止日期，并仅返回完成复制所需的数据。V1 不增加登录、验证码或频率限制。

**验证：** 测试游客可获取公开有效次卡的微信号；隐藏、过期、删除或不存在的次卡均不返回微信号；公开列表接口仍不泄露联系方式。

### 步骤 29：实现过期双重保障

**指令：** 按 `Asia/Shanghai` 配置每日过期任务，将截止日期当天 23:59:59 已结束的记录标记为过期隐藏；保留查询层实时排除条件，避免定时任务延迟导致曝光。

**验证：** 准备昨天、今天和明天到期的样例；确认昨天的记录立即不公开并被任务标记，今天和明天的记录仍按产品定义展示。

### 步骤 30：记录数据里程碑

**指令：** 更新 `memory-bank/architecture.md` 和 `memory-bank/progress.md`，记录真实表结构、关系、RLS 边界、联系方式接口、过期策略、迁移顺序和当前完成进度。

**验证：** 从全新开发数据库按文档重建并运行数据库测试；确认结果与现有开发环境一致。

## 5. 里程碑四：完成游客浏览与联系流程

### 步骤 31：建立用户端主题与布局

**指令：** 以 `memory-bank/assets/ui-reference.png` 为视觉参考，为 DanceCARD 定义深钴蓝、酸橙绿、薄荷绿、亮粉和浅紫蓝等 Neo-pop 色彩，以及字号、间距、大圆角、胶囊按钮和阴影变量；建立移动端安全区域、页面容器以及加载、错误和空状态的统一外观。只借鉴设计语言，不复制参考图角色或具体版式。

**验证：** 在窄屏和常见手机宽度渲染状态展示页；确认没有横向滚动、文字截断或底部安全区域遮挡；完成 H5 和微信小程序构建。

### 步骤 32：实现三级底部导航

**指令：** 实现“次卡、常见问题、我的次卡”三个一级入口，不增加“添加次卡”一级入口。

**验证：** 组件测试三个标签的选中状态与跳转；端到端测试刷新后路由正确；检查导航中不存在第四个业务入口。

### 步骤 33：建立跨端 API 客户端

**指令：** 在 api-client 包封装城市、区域、舞室、每页 20 条的次卡分页和联系方式读取；统一处理加载、错误、鉴权和平台差异。

**验证：** 使用模拟成功、空数据、权限错误和网络错误响应测试每类结果；确认用户端组件不直接依赖 CloudBase 具体实现。

### 步骤 34：实现城市选择页

**指令：** 从后端读取启用城市并按 sort_order 展示；点击城市后只传递稳定 ID 进入区域页。

**验证：** 组件测试排序、空状态和错误状态；端到端测试停用城市不可见、点击启用城市进入正确区域页。

### 步骤 35：实现行政区域选择页

**指令：** 根据城市 ID 加载启用行政区域，展示当前城市名称，并处理无效或停用城市。

**验证：** 测试仅显示所属城市的启用区域；直接访问无效城市 ID 时显示可恢复错误；点击区域进入对应舞室页。

### 步骤 36：实现舞室列表页

**指令：** 根据区域 ID 展示启用舞室名称；通过“找不到舞室”弹窗说明新增流程，并明确显示联系邮箱 `m18800126467@163.com`；不展示图片、评分、老师或距离。

**验证：** 测试舞室归属筛选和空状态；检查页面字段，确认未出现设计范围外的舞室信息；点击舞室进入正确次卡页。

### 步骤 37：实现舞室次卡列表

**指令：** 展示舞室名称、“添加次卡”按钮以及公开次卡的昵称、剩余课时、单节价格和发布时间；列表每页 20 条并保持价格升序、同价时间倒序。

**验证：** 使用混合状态数据确认只显示公开有效次卡；验证价格升序和同价时间倒序；验证空状态仍保留添加按钮。

### 步骤 38：实现次卡详情页

**指令：** 展示设计文档规定的全部公开字段、联系入口和免责声明，不直接渲染微信号。

**验证：** 组件测试全部字段的有值和选填为空场景；检查页面 DOM 和网络初始响应，确认没有微信号；过期或隐藏 ID 显示不可用状态。

### 步骤 39：实现联系卖家流程

**指令：** 点击昵称或联系按钮后直接调用受保护接口，并通过跨端复制适配器复制微信号；风险提示常驻在详情页，不增加二次确认弹窗。

### 步骤 59：实现用户管理

**指令：** 支持管理员查看必要用户资料和发布记录，并禁用或恢复用户；避免展示管理工作不需要的敏感数据。
